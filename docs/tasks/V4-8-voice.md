# V4-8：回复带语音（计划书 v4 功能八）——第一版

负责：Claude 实现，Codex 审查及 Windows 实测，负责人验收。分支：`task/v4-8-voice`，从 PR #38 的 `6775d81` 拉出（依赖 #38）。

## 这一版做了什么

1. **先修基线问题**（Codex 在 #38 实机发现）：
   - 已经 complete 并展示完的回复，会被下一轮 submit、挂断通话或退出时的 `interrupt` 追改成 cancelled，重启后显示“被打断”，全文索引也会漏掉这些消息。
   - 现在 `interrupt` 只取消还在生成中的那一轮。已经结束的轮次（complete / failed / cancelled / suppressed）保持原状态，不打“已打断”标记，也不撤回表情，只停掉还在念的语音。
   - 已完成的回复按全文记入上下文：全文都已在气泡里显示过。还在生成中被打断的朗读轮次，仍只记已经念出来的部分，真正的取消照旧。
   - 旧库里已经是 cancelled 的历史记录不做批量修改。
2. **默认开启朗读**：
   - `speech_enabled` 没有设置过（新库，或从没动过开关）时，默认开启。
   - 用户手动关过的保持关闭，启动时只提示一次：“现在可以让我开口说话啦”。
3. **智能朗读**（新的默认说话方式 `smart`，在 `speech/smart.py`）：
   - 短回复全念。
   - 长回复先念开头（约 120 字），之后只念要紧的话：问你的问题、要你做决定或去处理的事、句首是结论词的句子；结尾那句短的情绪话补上。一轮总共不超过约 300 字。
   - 清单只念条数和第一条；表格念成“我做了张表”；代码、链接、路径沿用原来的处理。
   - 重复的话不念第二遍。
   - 有内容被省掉时，最后补一句“剩下的写在气泡里啦”之类的提示，一轮最多一次，说法从几种里随机挑。
   - 分段：第一段只放一句，好让她尽快出声；之后每段 1～3 句、约 40～120 字。同一轮的两段之间停 250 毫秒。
   - 回复是流式的：第一句一出来就念，不等全文生成完。
   - 办事结果（`speak_reply`）也走同一套取舍。
   - 不额外调用模型。
4. **失败时退回本地朗读**：
   - 云端合成失败（没配声线、额度用完、服务出错）时，这一轮剩下的句子都改用系统朗读，回复照常完成，状态栏提示一次。
   - 只影响这一轮，下一轮重新尝试云端。
   - 日语配音本地念不了，仍按原来的方式报错。
5. **打断**：沿用 `speech.stop()`（新消息、说话打断、按停止都会清空队列，提升轮次让晚到的音频作废）。退回本地朗读后，晚到的云端音频也不会再播放。
6. 每轮念了多少字记入用量（`voice_characters`）。

## Codex 复核（9d86d02）三项 P2 的修复

1. 两段云端同时失败：本轮改成本地念的句子打上 `fell_back`，晚到的第二个云端失败当过期消息忽略，不再当成本地朗读出错去停播、清队列；云端返回坏音频也按合成失败退回本地。
2. 办事结果每份一个独立朗读轮次（`agent:<随机号>`），上一份退回本地 / 出错不影响下一份，云端恢复后重新用云端。
3. 长句不再整段念：SmartReader 遇到超过 120 字的一句先按逗号、分号、顿号、冒号切成小句再逐个取舍（还长就硬切），
   正文流式到达还是一次给完念出来都一样；清单、表格的概括句也占整轮预算。
4. 组合用例（`tests/test_voice_reply.py` ProductionQueueTests）：真正的 SpeechOutput 和 TaskWorker 线程并发合成，只把系统朗读引擎和播放器换成会按时念完的假对象；
   生产入口 `MainWindow.speak_reply` 连续两次（先失败后恢复）、一次性交付 781 字以上结果；四个用例在修复前都失败，修复后通过。

## 这一版没做（后续）

- `<say>` 口播版（可选项）；
- QQ 主人私聊发语音消息；
- “大肥鱼声线”设定：人格包里的声线描述、各服务的音色对应、固定台词逐条试听、语气词用新声线预先合成；
- 首次出声延迟、被打断比例这些对照数据。
- 计划书提到的“非完整朗读时偶尔回复失败”，这一版**仍没复现出原因**。现在云端失败会退回本地朗读，不再中断整轮，可能已经覆盖了一部分情况，需要实机再观察。
- 实机验证：云端声线还没配置，先验证系统朗读的回退；音色试听不算完成。
